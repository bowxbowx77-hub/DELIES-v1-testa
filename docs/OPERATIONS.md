# Розгортання та обслуговування

## Один сервер через Docker Compose

Потрібні Docker Engine і Compose v2. З кореня репозиторію:

```sh
docker compose up --build -d
docker compose ps
curl http://127.0.0.1:3000/api/health
```

Цей режим відкриває порт **лише на loopback хоста**. Контейнер працює як UID 10001. Акаунти, сесії, історія та блоби лежать у постійному томі `vault_data:/data`. Оновлення контейнера не видаляє том. **Не використовуйте `docker compose down -v` для системи з даними.**

### Публічний HTTPS-сервер

1. Спрямуйте DNS свого домену на сервер. Відкрийте TCP 80 та 443. Не відкривайте Gunicorn і його довірені proxy-заголовки напряму в інтернет.
2. Скопіюйте `.env.example` у `.env` та встановіть дійсний `DEVVAULT_DOMAIN`.
3. З кореня репозиторію виконайте:

```sh
docker compose -f compose.yaml -f deploy/https.compose.yaml up --build -d
docker compose -f compose.yaml -f deploy/https.compose.yaml logs --tail=40
```

Caddy видає TLS-сертифікат, обмежує розмір тіла запиту й пересилає запити на `devvault:3000`. Бекенд довіряє одному закритому reverse proxy; cookie позначено Secure. Статичний фронтенд і API мають спільний origin. Для власного reverse proxy передавайте `Host`, `X-Forwarded-Proto`, реальну адресу клієнта; обмежте тіло до 130 MiB та дозвольте до 240 секунд для великих операцій. Публічні посилання включають ваш домен — не змінюйте його без перенаправлення.

### Увімкнути ClamAV в контейнері

Додайте третій Compose-файл до команди розгортання:

```sh
docker compose -f compose.yaml -f deploy/https.compose.yaml -f deploy/scanner.compose.yaml up --build -d
```

Ця конфігурація збирає образ зі сканером, запускає `freshclam` для баз сигнатур у власному томі й монтує їх у застосунок **тільки для читання**. Перед першим запуском API очікує готовності бази. Для початкового завантаження та оновлень потрібен інтернет. Якщо база не завантажилася, перевірте журнал `signatures`; не вимикайте перевірку, щоб обійти помилку. За `DEVVAULT_SCAN=1` помилка сканера блокує імпорт, не публікуючи жодних файлів. Для локального тесту без TLS можна об’єднати лише `compose.yaml` та `deploy/scanner.compose.yaml`.

## Без Docker

Зберіть UI за інструкцією в README. Створіть окремого непривілейованого користувача, приватний каталог даних (режим `0700`) і каталог для резервних копій. Залежності й код мають бути доступні для читання, каталог даних — для запису.

```sh
npm ci
npm run setup:server
npm run build
export DEVVAULT_DATA=/srv/devvault/data
export PORT=3000
python3 scripts/serve.py
```

Для постійної роботи використовуйте системний менеджер процесів. Наприклад, у systemd задайте `User=devvault`, `WorkingDirectory=/opt/devvault`, `ExecStart=/opt/devvault/.venv/bin/python /opt/devvault/scripts/serve.py`, `Restart=on-failure`, `UMask=0077` та `Environment=DEVVAULT_DATA=/srv/devvault/data`. Дозвольте доступ до порту тільки з reverse proxy. Увімкніть TLS перед публічним використанням.

| Змінна | Значення / призначення |
|---|---|
| `DEVVAULT_DATA` | Шлях поза публічною директорією сайту. Типово `vault-data` у репозиторії; у контейнері `/data`. |
| `PORT` | Порт сервера, типово `3000` для Gunicorn / `5173` для Vite. |
| `WEB_CONCURRENCY` | Кількість Gunicorn workers: типово 2 із чотирма потоками в кожному. |
| `DEVVAULT_HTTPS=1` | Secure cookie і HSTS для HTTPS-середовища. Не вмикайте для локального HTTP. |
| `DEVVAULT_ORIGIN` | Канонічний origin публічного інтерфейсу, наприклад `https://vault.example.org`. |
| `DEVVAULT_TRUST_PROXY=1` | Довіряти **одному** reverse proxy. Тільки якщо немає прямого зовнішнього доступу до бекенду. |
| `DEVVAULT_SCAN=1` | Вимагати успішне сканування ClamAV перед публікацією вмісту. |

`.env` читається Compose; для запуску без Docker змінні слід експортувати в середовище процесу.

## Резервна копія

Інструмент локального адміністратора: зовнішнього API для копіювання всієї БД немає.

```sh
.venv/bin/python scripts/maintenance.py --data vault-data backup backups/vault-2026-11-18.tar.gz
```

Назва файлу має бути новою. Інструмент бере SQLite online backup та фіксує потрібні незмінні блоби hardlink-ами, поки утримує блокування запису. Якщо FS не підтримує hardlink для блобів, робиться копія. Стиснення відбувається вже після звільнення блокування. Копія містить реальні приватні файли та хеші паролів, **але не чинні сесії**. Вихідний каталог і файл не повинні бути загальнодоступними. Зберігайте копії на FS із підтримкою атомарних hardlink у вихідному каталозі.

У контейнері:

```sh
# Використовуйте унікальний timestamp для кожного запуску.
docker compose exec -T devvault python scripts/maintenance.py --data /data backup /backups/vault-20261118T020000.tar.gz
docker compose cp devvault:/backups/vault-20261118T020000.tar.gz ./vault-20261118T020000.tar.gz
```

Для щоденного резервування, наприклад у crontab системного користувача (відкоригуйте шляхи):

```cron
15 2 * * * cd /opt/devvault && .venv/bin/python scripts/maintenance.py --data /srv/devvault/data backup /srv/devvault/backups/vault-$(date -u +\%Y\%m\%dT\%H\%M\%SZ).tar.gz
```

Розклад не активується автоматично. Шифруйте й переносіть резервні копії на інший носій, обмежуйте доступ, налаштуйте строк зберігання та сповіщення про помилки. Копія на тому самому диску не захищає від втрати сервера.

### Відновлення

Використовуйте лише власні довірені архіви. Потрібен **новий, неіснуючий каталог**:

```sh
.venv/bin/python scripts/maintenance.py restore backups/vault-2026-11-18.tar.gz /srv/devvault/restored-check
```

Перевіряються SHA-256 кожного блоба, розміри, відповідність усім посиланням маніфестів, цілісність SQLite та зовнішні ключі. Програма відмовиться перезаписати існуюче сховище. Зупиніть сервіс, переключіть `DEVVAULT_DATA` на перевірений каталог із правильним власником та перезапустіть. Старий том зберігайте до підтвердження відновлення. Акаунтам треба увійти повторно. Гостьові сесії з копії не відновлюються.

Після аварійного завершення можуть залишитися блоби без посилань. Перевірка без видалення:

```sh
.venv/bin/python scripts/maintenance.py --data vault-data gc
# Після перевірки й резервування, видалити тільки блоби без жодного посилання:
.venv/bin/python scripts/maintenance.py --data vault-data gc --apply
```

Не очищуйте `stage` під час активних імпортів чи експорту. Видалення репозиторію з живої бази не знищує старі резервні копії.

## Межі поточної архітектури

Поточна конфігурація розрахована на один хост із локальним диском. SQLite працює у WAL; writer-транзакції серіалізують зміни та збір сміття. Підготовка/перевірка завантаження відбувається до транзакції, великі дані проходять через тимчасові файли, ZIP для скачування створюється на диску. Знімки дублюють лише метадані; вміст дедуплікується між версіями. Зведення поточної версії й індекс зайнятого місця оновлюються в тій самій транзакції. Каталог і журнал мають пагінацію.

Моніторте `/api/health`, вільний диск, inode, час резервування і журнали worker-ів. SQLite/WAL не слід ділити через мережеву FS між кількома хостами. Для горизонтального масштабування наступний крок — PostgreSQL для метаданих, закрите object storage для блобів і фонові воркери імпорту/сканування; це план розвитку, не заявлена поточна можливість.
